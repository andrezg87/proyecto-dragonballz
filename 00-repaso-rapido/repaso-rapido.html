1 · La web y las APIs 01 y 02

Tu navegador pide archivos o datos a un servidor, y el servidor responde. Una API responde con datos (JSON), no con páginas.

Navegador (cliente)→ petición GET →Servidor / API→ respuesta 200 + JSON →Tu código la pinta

HTTP

  • GET leer · POST crear · PUT/PATCH cambiar · DELETE borrar
  • 200 ok · 404 no existe · 500 falló el servidor

JSON

Texto con forma de objeto: claves entre comillas dobles, sin comentarios ni coma final.

const obj = JSON.parse('{"id":25,"name":"pikachu"}');  // texto -> objeto
const texto = JSON.stringify(obj);                      // objeto -> texto
Error típico

Olvidar que la respuesta llega como texto y hay que convertirla (respuesta.json()).

2 · HTML 01

HTML dice qué hay en la página: estructura y contenido, con etiquetas.

<header><h1>Mi página</h1></header>
<main>
  <section id="lista">
    <article class="card"><h2>Goku</h2><img src="goku.png" alt="Goku"></article>
  </section>
</main>

Semántica

header, nav, main, section, article, footer: describen su contenido en vez de usar solo div.

Atributos

id (único), class (reutilizable), href, src, alt (siempre en imágenes).

Error típico

Imagen sin alt, o id repetido en dos elementos.

3 · CSS 01

CSS dice cómo se ve: selector { propiedad: valor; }.

:root { --acento: #f58a1f; }                 /* variable */
* { box-sizing: border-box; }                  /* el padding no agranda la caja */
.card { background: white; padding: 16px; border-radius: 12px; }
.card:hover { transform: translateY(-4px); }   /* pseudoclase */
#lista { display: grid; grid-template-columns: repeat(auto-fill, minmax(180px, 1fr)); gap: 16px; }
@media (max-width: 500px) { #lista { gap: 8px; } }  /* responsive */

Selectores y cascada

Etiqueta < clase < id < style="" en fuerza. Si empatan, gana la regla de más abajo.

Modelo de caja

Contenido + padding + border + margin. Usa siempre box-sizing: border-box.

Flexbox y Grid

Flex: en fila o columna (justify-content, align-items). Grid: en cuadrícula.

Tailwind

Clases utilitarias en el HTML: p-4 rounded-xl bg-white hover:-translate-y-1. Prefijos sm: md: lg: = responsive.

Error típico

Escribir la clase sin el punto en CSS (card en vez de .card), o poner display:flex en los hijos en lugar del padre.

5 · Asincronía y fetch 02

Pedir datos tarda. JS no se congela esperando: usa promesas, y async/await las hace leer de arriba a abajo.

async function getJSON(url) {
  const respuesta = await fetch(url);              // 1) llega estado y encabezados
  if (!respuesta.ok) throw new Error(`HTTP ${respuesta.status}`); // fetch NO falla con 404
  return respuesta.json();                         // 2) llega el cuerpo -> objeto
}

try {
  const datos = await getJSON("https://pokeapi.co/api/v2/pokemon/pikachu");
} catch (error) {
  mostrarError();                                  // sin internet, 404, etc.
}

const todos = await Promise.all(urls.map(getJSON)); // a la vez: tarda lo del más lento

Promesa

pending → fulfilled (valor) o rejected (error).

async / await

Una función async siempre devuelve una promesa. await pausa solo esa función.

Errores típicos

Faltar un await (sale Promise { <pending> }); no revisar respuesta.ok; hacer await uno tras otro cuando pueden ir juntos con Promise.all.

6 · TypeScript 02

TypeScript es JavaScript con tipos: te avisa de errores antes de ejecutar. Los navegadores no lo entienden: se compila a JS y los tipos desaparecen.

interface Pokemon { id: number; name: string; types: string[]; nick?: string; }

type Tipo = "fire" | "water" | "grass";            // literales / unión

async function getJSON<T>(url: string): Promise<T> {   // genérico
  const r = await fetch(url);
  if (!r.ok) throw new Error(`HTTP ${r.status}`);
  return r.json();
}

const p = await getJSON<Pokemon>("https://pokeapi.co/api/v2/pokemon/25");

function esPokemon(v: unknown): v is Pokemon {      // type guard
  return typeof v === "object" && v !== null && typeof (v as Pokemon).id === "number";
}

Para qué sirve

Autocompletar, detectar typos (pokemon.nmae) y campos que faltan.

Utility types

Partial, Pick, Omit, Readonly, Record<K, V>.

Error típico

Creer que TS valida lo que llega de la red: getJSON<Pokemon> es una promesa tuya; en ejecución los tipos ya no existen. Y editar main.ts sin compilar: el navegador carga main.js.

7 · De los datos a la pantalla 03

Toda la Pokédex sigue un mismo camino. Si lo entiendes, puedes armar cualquier app con una API.

API (JSON)→getJSON<T>→Adaptador→Estado→render()→HTML
PiezaQué hacePor qué existe
interface de la APIDescribe lo que devuelve el servidorAutocompletado y errores de tipo
Adaptador (aPokemon)Convierte la forma de la API a la de tu tarjetaSi la API cambia, solo tocas un lugar
tarjeta()Recibe un dato y devuelve su HTMLUna sola plantilla para todos los elementos
Estado + render()Guardas qué mostrar y lo dibujas desde ceroBuscador, filtros y paginación sin lío
Delegación de eventosUn solo listener en el contenedorCientos de botones sin cientos de listeners
try/catch + estadosCargando, error, vacíoEl usuario nunca ve una pantalla rota
Clave para el proyecto

Otra API = otra forma de JSON. Reutilizas la arquitectura, pero comprueba siempre con el JSON real: nombre del arreglo, paginación, tipo de cada campo y qué responde cuando algo no existe.

8 · Git nuevo · docs/GIT-BASICO.md

Git guarda el historial de tu proyecto y te deja volver atrás; GitHub guarda una copia en internet. Una rama es una línea de trabajo independiente.

Videos para aprender Git
  • 🎬 Empieza por aquí (2 min 30 s): ¿Qué es Git y GitHub? Repositorios, ramas y mucho más
  • 📚 Curso completo en español: Curso de Git y GitHub (desde cero)
  • ⏱️ Curso de 1 hora (en inglés, activa los subtítulos): Git Tutorial for Beginners: Learn Git in 1 Hour

¿Para qué sirve?

Sin Git

Carpetas como proyecto_final, proyecto_final2, proyecto_final_ahora_si. Si algo se rompe, no sabes qué cambió ni cómo volver.

Con Git

Un solo proyecto con un historial de «puntos de guardado» con mensaje. Puedes ver qué hiciste, cuándo, y probar cosas sin dañar lo que ya funciona.

Y GitHub sirve para tres cosas: respaldar tu trabajo en internet, compartirlo (tu profesor lo ve) y que servicios como Vercel lo lean para publicar tu página.

Las palabras que vas a oír

PalabraQué esAnalogía
RepositorioTu carpeta del proyecto más su historial (una carpeta oculta llamada .git)El cuaderno completo con todas sus páginas
CommitUn punto de guardado: una «foto» de todo tu proyecto con un mensaje y un código (por ejemplo 5be30ca)«Guardé la partida aquí: terminé el nivel 1»
Rama (branch)Una línea de commits independiente. Al cambiar de rama, tus archivos cambian para mostrar cómo estaban en esa ramaUn universo alterno donde pruebas sin dañar el principal
Zona de preparación (staging)Lo que marcaste con git add para el próximo commitLa caja donde pones cosas antes de sellarla
Remoto (origin)La copia de tu repositorio que está en GitHubLa partida guardada en la nube

El recorrido de tu trabajo

Editas archivos→ git add →Zona de preparación→ git commit →Historial local→ git push →GitHub

commit guarda solo en tu computador. Hasta que no haces push, GitHub no se entera. pull hace el camino contrario: trae de GitHub lo que no tienes.

Los comandos del proyecto

git status                    # ¿dónde estoy y qué cambió? (tu brújula)
git checkout -b nivel-1       # crear la rama nivel-1 y moverme a ella
git add .                     # preparar TODOS los cambios (el punto = todo)
git commit -m "Nivel 1: HTML" # guardar un punto en mi historial local
git push -u origin nivel-1    # subir la rama a GitHub (la primera vez lleva -u origin)
git push                      # las siguientes veces basta con esto
git checkout nivel-3          # moverme a una rama que ya existe
git branch                    # listar mis ramas (la que tiene * es donde estoy)
git log --oneline             # ver mis commits, uno por línea
git pull                      # traer lo nuevo de GitHub

Un ejemplo completo, con lo que verás en pantalla

Estás en la rama nivel-1 y acabas de crear tu index.html:

$ git status
On branch nivel-1
Untracked files:
  (use "git add <file>..." to include in what will be committed)
        04-proyecto/dragonball/nivel1/

nothing added to commit but untracked files present

Git te dice: «hay archivos nuevos que todavía no sigo». Los preparas:

$ git add .
$ git status
On branch nivel-1
Changes to be committed:
        new file:   04-proyecto/dragonball/nivel1/index.html

Están en la caja (zona de preparación), listos para sellar. Ahora el commit:

$ git commit -m "Nivel 1: HTML con 5 personajes"
[nivel-1 5be30ca] Nivel 1: HTML con 5 personajes
 1 file changed, 40 insertions(+)
 create mode 100644 04-proyecto/dragonball/nivel1/index.html

$ git status
On branch nivel-1
nothing to commit, working tree clean

«Working tree clean» significa que todo está guardado. Falta subirlo a GitHub:

$ git push -u origin nivel-1
 * [new branch]      nivel-1 -> nivel-1
branch 'nivel-1' set up to track 'origin/nivel-1'.

$ git log --oneline
5be30ca (HEAD -> nivel-1, origin/nivel-1) Nivel 1: HTML con 5 personajes

Ya está en tu GitHub. origin/nivel-1 junto al commit confirma que GitHub tiene el mismo punto que tu computador.

Si tu Git habla español

Según cómo esté instalado, los mensajes pueden salir en español («En la rama nivel-1», «nada para hacer commit»). Significan lo mismo.

9 · Publicar en internet nuevo · bonus nivel 8

Vercel lee tu repositorio de GitHub y publica tu página con una URL pública. Cada git push a la rama publicada vuelve a desplegar.

# vercel.toml: las 3 preguntas de Vercel
installCommand = "npm install"            # ¿qué instalo?
buildCommand = "npm run build"            # ¿cómo construyo? (TS -> JS)
outputDirectory = "04-proyecto/dragonball/nivel7"  # ¿qué carpeta publico?

Qué rama se publica

La de Settings → Environments → Production → Branch Tracking. Redeploy no cambia de rama.

Para que la vea cualquiera

Comparte el dominio de producción y desactiva Vercel Authentication si pide login. Pruébalo en incógnito.

Autoevaluación rápida

Responde en tu cabeza (o en voz alta) y abre la respuesta para comprobar.

1. ¿Qué diferencia hay entre HTML, CSS y JavaScript?

HTML dice qué hay, CSS cómo se ve y JavaScript qué hace.

2. ¿Por qué fetch necesita dos await?

El primero espera la respuesta (estado y encabezados) y el segundo espera y convierte el cuerpo con .json().

3. Pides un id que no existe. ¿fetch lanza error?

No: responde con otro código (por ejemplo 404) y respuesta.ok es false. Solo lanza error si no hay conexión.

4. ¿Qué devuelve una función async sin await?

Una Promise.

5. ¿Cuándo usas Promise.all?

Cuando tienes varias peticiones independientes: salen a la vez y el tiempo total es el de la más lenta.

6. Tu interface dice number pero la API manda texto. ¿Qué pasa al ejecutar?

Nada lo detecta: los tipos se borran al compilar y el dato sigue siendo texto.

7. ¿Por qué el navegador carga main.js y no main.ts?

El navegador no entiende TypeScript; el compilador lo convierte a JavaScript.

8. ¿Para qué sirve un adaptador?

Convierte la forma del JSON de la API a la forma que usa tu aplicación, y aísla los cambios de la API en un solo lugar.

9. (Tema nuevo del proyecto) ¿Qué diferencia hay entre git add, commit y push?

add prepara los cambios, commit los guarda en tu historial local y push los envía a GitHub.

10. ¿Qué tres preguntas contesta vercel.toml?

Qué instalo, cómo construyo y qué carpeta publico.
