Proyecto Dragon Ball: analiza y replica

Exploras una API, diseñas una página, la construyes y al final analizas tu propio código. Lo que se evalúa es que puedas explicar, con tus palabras, por qué funciona.

El encargo. Tu sobrino quiere una página para ver sus personajes favoritos de Dragon Ball. Te contrataron para hacerla y te entregaron la paleta de colores de la serie. Tu trabajo: diseñarla y construirla. La página tiene solo dos pantallas: un listado con buscador y filtros, y el detalle de un personaje, en web y en celular.
Antes de empezar. Sigue el README.md de la raíz del repositorio: instala Node.js y Git, ejecuta npm install y comprueba con npm run verificar que todo está listo. Tu trabajo va en la carpeta 04-proyecto/dragonball/. Para crear un nivel usa npm run nivel -- N y para compilar tu TypeScript, npm run build.
Cómo se trabaja con la IA en este proyecto. La IA puede escribir el código, pero tú diriges. No tienes que teclear todo desde cero, y tampoco se trata de pedirle el proyecto entero y pegarlo. Tu trabajo es: darle contexto real (wireframe, paleta, el JSON de la API), pedirle el código por piezas pequeñas, acomodar cada pieza en el archivo y la carpeta correctos dentro de VS Code, ejecutarla, entenderla, corregirla y conversarla: preguntar por qué, pedir alternativas y cuestionar lo que no tenga sentido. Lo que escribes tú, con tus palabras, es la Parte D y tu README (como mínimo un párrafo por respuesta, sin pegar texto generado). Todo lo sustentas en vivo. Tus respuestas se guardan solas en este navegador.

A · Explora la API 15 %

Dónde leer sobre la Dragon Ball API. Empieza por la documentación y luego comprueba todo con el JSON real:
  • web.dragonball-api.com: el sitio de la API.
  • web.dragonball-api.com/documentation: la documentación (endpoints, parámetros y ejemplos).
  • dragonball-api.com/api-docs: documentación interactiva (Swagger UI), donde puedes probar cada endpoint desde el navegador y ver la forma exacta de la respuesta.
Bonus ★: si vas a hacer el bonus de planetas, explora también /planets (lista y detalle) y compara su forma con la de los personajes.
La documentación te da el mapa; el JSON real manda. Si algo no coincide, anótalo: puede ser una diferencia importante.

C · Construye 30 % + bonus

Trabaja dentro de 04-proyecto/dragonball/, con una subcarpeta por nivel (nivel1 … nivel7). Créalas con npm run nivel -- 3 (ya dejan lista la configuración de TypeScript) y compila con npm run build. Al terminar, tu página debe verse como tu diseño. Crea una rama y haz commits en cada nivel (ver el recuadro de Git).

Git: una rama por nivel, en tu GitHub. Vas a guardar tu avance con Git de forma ordenada. Git es un tema nuevo, que no se vio en clase: se aprende aquí y se retoma más adelante, en Angular, con Pull Requests, Issues y hotfixes. Empieza con este video introductorio de 2 minutos y medio: ¿Qué es Git y GitHub? Repositorios, ramas y mucho más. Luego lee docs/GIT-BASICO.md y, si quieres profundizar, mira este video: Curso de Git y GitHub (desde cero). Los comandos que usarás:

Cada nivel nace de la rama del anterior (nivel-1 → nivel-2 → … → nivel-7). Los comandos de Git los escribes tú, no la IA: así aprendes qué hace cada uno.
Tu repositorio de GitHub debe ser público (Public), para que tu profesor pueda ver tus ramas y para poder publicarlo en Vercel.
El ciclo de cada pieza de código.
  1. Pídela pequeña: una función o una sección, no todo el nivel. Dale tu contexto (diseño, JSON real, decisiones).
  2. Pregunta dónde va y por qué: ¿en qué archivo?, ¿antes o después de qué?
  3. Acomódala tú en VS Code: crea o abre el archivo correcto y pégala en el lugar indicado.
  4. Ejecútala: npm run build, recarga la página y mira qué pasa.
  5. Si falla, entiéndelo antes de pedir el arreglo: ¿qué dice el error y qué crees que lo causa?
  6. Explícasela a la IA con tus palabras y pídele que te corrija si algo está mal. Solo entonces pasa a la siguiente pieza.
Ojo: una IA puede darte código de “la forma típica” que no encaja con esta API. Detectar y corregir esos errores es parte del trabajo.
Recomendación. Usa el chat de Claude o de Gemini: te da el código en bloques y tú lo acomodas en VS Code, lo ejecutas y lo conversas. Con agentes que escriben los archivos por ti, como Claude Code u OpenCode, ya no acomodas nada y se aprende menos. Es una sugerencia: si usas Claude Code, este repositorio lo configura para que te entregue el código en la conversación en vez de escribir tus archivos. En docs/PROMPTS-CHAT.md tienes un prompt para convertir el chat en tu tutor y en docs/USAR-IA.md cómo usar Claude Code como tutor (/asistir-proyecto).
Nivel 8 · Bonus (+10 %): publica tu página en Vercel.

¿Qué es Vercel? Es una plataforma de hosting: un servicio que guarda tu página en servidores de internet y la deja disponible para cualquier persona con un enlace, por ejemplo mi-dragonball.vercel.app. Tiene un plan gratuito para proyectos personales y conecta con GitHub: cada vez que subes cambios, vuelve a publicar tu página sola y le pone HTTPS.

¿Para qué sirve aquí? Hasta ahora tu página solo existe en tu computador (file:// o un servidor local). Con Vercel puedes mandarle el enlace a tu sobrino, abrirla desde tu celular y probar que realmente funciona en internet, no solo en tu máquina. Además, queda como parte de tu portafolio.

Mira primero el ejemplo resuelto. En el repositorio del curso hay una rama que ya despliega la Pokédex con este mismo método: deploy-vercel-pokeapi-nivel-8. Lee su DEPLOY-VERCEL.md (explica el vercel.toml línea por línea) y compárala con main. Tu trabajo es hacer lo equivalente con tu proyecto, en tu repositorio, desplegando tu rama nivel-8.

Pasos

  1. Crea una cuenta gratuita en vercel.com (lo más fácil es entrar con tu cuenta de GitHub).
  2. Con tu nivel 7 terminado y subido, crea la rama del bonus desde nivel-7: git checkout nivel-7, git checkout -b nivel-8 y git push -u origin nivel-8 (si hiciste el bonus de planetas, créala desde bonus-planetas para publicarlos). Esa es la rama que vas a desplegar; no hace falta tocar main.
  3. Comprueba que en nivel-8 existe 04-proyecto/dragonball/nivel7/ con tu index.html y tu main.ts, y que npm run build compila sin errores en tu computador. Si quieres ayuda guiada, usa /asistir-bonus en Claude Code o el prompt 7 de docs/PROMPTS-CHAT.md.
  4. En Vercel: Add New → Project, elige tu repositorio y pulsa Import. El primer despliegue puede fallar: Vercel empieza por main, que no tiene tu nivel7. Es normal.
  5. En el proyecto de Vercel entra a Settings → Environments → Production → Branch Tracking, cambia el nombre de la rama de main a nivel-8 y pulsa Save. Así Vercel publica tu rama del bonus como «producción».
  6. No cambies nada en Root Directory, Build Command ni Output Directory (abre vercel.toml: tiene un comentario en cada línea): el archivo vercel.toml del repositorio ya le dice a Vercel que instale las dependencias, compile tu TypeScript con npm run build y publique 04-proyecto/dragonball/nivel7.
  7. Crea el despliegue de tu rama: pestaña Deployments → botón Create Deployment, escribe nivel-8 y pulsa Create Deployment. (Ojo: el botón Redeploy no sirve para cambiar de rama; solo repite el despliegue de main.) Al terminar te da una URL pública.
  8. Haz que cualquiera pueda abrirla, sin cuenta de Vercel. Copia la URL del dominio de producción (la corta, del tipo tu-proyecto.vercel.app, que aparece en Domains; no la URL larga de un despliegue concreto). Ábrela en una ventana de incógnito: si te pide iniciar sesión en Vercel, ve a Settings → Deployment Protection, desactiva Vercel Authentication y pulsa Save. Vuelve a probar en incógnito.
  9. Ábrela en tu celular y comprueba que el buscador, los filtros y el detalle funcionan. Haz un cambio pequeño en nivel-8, haz git push y mira cómo Vercel publica la nueva versión.

Qué entregas: la URL en el README y una captura de la página abierta en tu celular.

Si algo falla
  • «No encuentro 04-proyecto/dragonball/nivel7/index.html» o «No Output Directory named "public" found»: la rama que Vercel está desplegando no tiene tu carpeta nivel7. Revisa que el Branch Tracking de Production sea nivel-8, que hiciste git push de esa rama y que en GitHub esa rama muestra 04-proyecto/dragonball/nivel7. Si Vercel sigue desplegando main, es normal que falle. Si moviste otros ajustes, devuélvelos a los valores por defecto.
  • Al abrir la URL me pide iniciar sesión en Vercel: es la protección de despliegues. Comparte el dominio de producción (el corto) y, si sigue pidiéndolo, desactiva Vercel Authentication en Settings → Deployment Protection.
  • Error 404 al abrir la URL: tu index.html no está dentro de nivel7.
  • La página sale pero sin datos: abre DevTools → Console y Network. Seguramente la ruta del <script src> está mal escrita (debe apuntar a main.js) o el build falló: revisa el registro del despliegue en Vercel.
  • Funciona en tu PC y no en Vercel: el servidor distingue mayúsculas de minúsculas (Main.js ≠ main.js) y solo acepta peticiones https.
  • El despliegue falla en «Build»: ejecuta npm run build en tu computador; si falla ahí, es un error de tipos de tu nivel7/main.ts. Vercel hace exactamente lo mismo.
Bonus · Planetas ★ (+15 %): diseño, código y despliegue.

Trabaja también con los planetas de Dragon Ball, no solo con los personajes. Tiene tres partes y las tres cuentan:

  1. Diseño: con Stitch o Claude Design, el listado y el detalle de planetas en web y móvil, con la misma paleta (mira el apartado «Bonus · Planetas» del wireframe). Guarda el prompt y una iteración, como en la parte B.
  2. Código: una pestaña Planetas en tu página, con listado de /planets (imagen, nombre y si está destruido), búsqueda por nombre, filtro por estado y detalle al hacer clic. En el detalle de un personaje, su planeta de origen debe llevar al detalle de ese planeta. Define tu interface a partir del JSON real y reutiliza getJSON<T> y la idea del adaptador.
  3. Despliegue: los planetas deben verse en tu página publicada en Vercel. Por eso este bonus se completa junto con el nivel 8.

Git: haz el código de planetas en una rama bonus-planetas creada desde nivel-7 (git checkout nivel-7, git checkout -b bonus-planetas), dentro de la misma carpeta nivel7. Si además haces el nivel 8, crea nivel-8 desde bonus-planetas para publicar la versión con planetas.

Si copias la Pokédex tal cual, algo se va a romper porque esta API responde distinto. Es buena señal: anota en el README cada error, su causa y cómo lo resolviste.
Pistas si te atascas
  • Lista vacía: compara el nombre del arreglo en tu interfaz con el del JSON real.
  • El ki no es un número: mira su formato antes de decidir si lo conviertes.
  • El buscador falla al recorrer: imprime la respuesta y compárala con la de la lista normal.
  • Con Tailwind por CDN puedes definir colores propios con tailwind.config, como en el paso 7 de la Pokédex.

D · Analiza tu código 25 %

Cuando termines, lee tu proyecto como si lo hubiera escrito otra persona. Aunque una IA haya generado partes del código, es tu proyecto y debes poder explicarlo. Puedes pedirle ayuda a una IA para entender algo, pero cada respuesta abierta la escribes tú: un párrafo como mínimo (unas 50 palabras), con tus palabras. Si no entiendes algo, dilo.

Preguntas abiertas (8)

  1. Cuenta cómo viaja un dato desde la API hasta la pantalla en tu proyecto. Nombra los archivos y funciones tuyos por los que pasa y qué le ocurre en cada uno.
  2. Explica con tus palabras qué hace async/await en tu código: por qué la página no se congela mientras llegan los datos, qué hace cada await y qué pasaría si lo quitaras.
  3. Escoge el fragmento que más te costó. ¿Qué hace, línea por línea? ¿Qué intentaste antes de que funcionara y qué aprendiste?
  4. De lo que vimos en clase con la Pokédex, ¿qué reutilizaste casi igual y qué tuviste que cambiar porque esta API responde distinto? Explica por qué.
  5. Rompe tu proyecto a propósito (quita un await, usa una URL que no exista, apaga el internet…). Primero escribe qué crees que pasará; luego pruébalo y explica si acertaste y por qué.
  6. ¿Dónde te ayudó TypeScript? Copia un error real que te salió, explica qué decía y cómo lo resolviste. ¿Qué cosas no puede comprobar por ti?
  7. Compara tu diseño con lo que construiste: ¿qué decisión de diseño tuviste que cambiar al programarla y por qué? ¿Cómo manejaste los estados de cargando, error y sin resultados?
  8. Si tuvieras una semana más, ¿qué mejorarías de tu proyecto y por qué? ¿Qué parte de tu código todavía no entiendes del todo?

Selección múltiple (4)

Elige una opción por pregunta. Si dudas, vuelve a probarlo en tu código.

  1. Tu fetch pide un personaje que no existe y el servidor responde con un error HTTP. ¿Qué ocurre si no revisas nada?
  2. ¿Qué devuelve una función async cuando la llamas sin await?
  3. Tu interface dice ki: number, pero la API devuelve el texto "60.000.000". ¿Qué pasa cuando la página corre en el navegador?
  4. Tienes 10 peticiones independientes. ¿Qué ventaja da Promise.all frente a un await dentro de un for?

Entrega y sustentación

  • Entrega: el enlace a tu repositorio público de GitHub, con la carpeta dragonball/ + README.md con tus respuestas de las partes A y D (botón de abajo), las 4 capturas del diseño con su prompt e iteración, la decisión sobre Promise.all, la bitácora de errores, la bitácora de conversación con la IA, tus comandos de Git y, si hiciste el bonus, la URL de Vercel.
  • Sustentación (10 min): recorre en voz alta el camino de un dato de la API a la pantalla, explica tus decisiones de diseño, di dónde TypeScript te ayudó y dónde no puede, y haz un cambio en vivo (un campo nuevo o un filtro). Puedes usar la IA para hacerlo, pero debes decir qué le pides, en qué archivo va y qué cambió. También muestra tu historial de ramas y commits en GitHub y explica qué hace cada comando de Git que usaste.
